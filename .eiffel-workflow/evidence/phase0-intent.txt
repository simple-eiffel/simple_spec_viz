### Intent Content Summary

#### What simple_spec_viz Does
- Loads JSON specifications (GUI_JSON_SPEC_PROTOCOL.md format)
- Generates state machine diagrams as SVG (states, transitions, guards, actions)
- Generates screen mockups as SVG (layout with widgets)
- Generates traceability matrix as Markdown (requirements → states → screens)
- Provides CLI tool: `simple_spec_viz visualize <spec.json> --output <dir>`

#### Why It's Needed
- Developers cannot visualize specs until implementation (late feedback)
- This tool enables early validation (shift-left)
- Result: Fewer rework cycles, faster feedback, better dev+AI collaboration

#### Controlled by Reference Docs Vision
- WIDGET_CATALOG.md (40+ widgets with JSON formats)
- STATE_MACHINE_GUIDE.md (10+ state machine patterns)
- 7 canonical examples (auth_flow, data_entry_form, crud_application, dashboard, wizard, settings, loading_pattern)

#### Key Design Decisions Locked

1. **MML Decision: YES - Required**
   - Frame conditions on all collection mutations
   - Model queries: states_model, screens_model
   - Invariants verifiable (no duplicate state IDs)

2. **Dependencies: simple_* First**
   - simple_json (JSON parsing)
   - simple_graphviz (state diagram rendering)
   - simple_file (file I/O)
   - simple_process (subprocess for GraphViz)
   - simple_mml (frame conditions)
   - base ISE (core types)
   - NO ISE/Gobo alternatives used

3. **Scope: MVP Focused**
   - Phase 1: Load specs, generate diagrams, error handling
   - Phase 2+: Docs integration, PNG/PDF export, interactive SVG
   - NOT: Interactive editor, code generation, WebUI

#### Design Principles
1. Simplicity over features (do one thing well)
2. Spec-first design (research → design drives implementation)
3. Visual clarity (diagrams understandable at a glance)
4. Error guidance (messages help users fix issues)
5. Eiffel idioms (DBC, void safety, SCOOP)
6. Facade pattern (hide complexity behind SIMPLE_SPEC_VIZ)
7. Immutability (loaded spec doesn't change)
8. Stateless generators (run independently)

### Information Status

**Vague terms that need clarification in review:**
- "Fast enough" (< 5 seconds for typical specs - needs definition of "typical")
- "Human-readable" (clear state names, visible transitions - measurable?)
- "Clear messages" (specific error message examples needed)
- "Production-ready" (what quality bar? coverage? performance?)

**Hidden assumptions that need surfacing in review:**
- Users know what a state machine is
- Users can read/write JSON
- Users understand Eiffel/DBC concepts (maybe not - reference docs should help)
- GraphViz is installed (what if not? graceful fallback?)
- 7 examples are sufficient test cases (are they?)

**Edge cases to clarify in review:**
- Empty specs (0 states) - should error or output empty diagram?
- Circular transitions (state A → state B → state A) - supported?
- Missing required fields (state without ID, transition without source) - error msg?
- Widget references to non-existent widgets in WIDGET_CATALOG - warn or error?
- Specs with 100+ states (performance target? timeout? limit?)
